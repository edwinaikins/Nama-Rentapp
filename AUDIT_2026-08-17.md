# NAMA Rent App — Full Codebase Audit
Date: August 17, 2026

Seven parallel reviews covered every file in the app: core state/auth, the dashboard, settings/admin, application & asset registry, registration & document-generation, services/utils/server, and the build/deploy pipeline. This is the synthesized, deduplicated result, ordered by how much damage each issue can do.

## Critical — fix before anything else

**1. Firestore security rules only check "is signed in," not role.** `firestore.rules` requires `request.auth != null` for every collection but never checks the caller's actual role. This was flagged independently by four separate reviews. In practice: any authenticated staff account — including a REGISTRAR, or even a brand-new self-registered account still sitting in `PENDING` status — can open the browser console and use the already-loaded Firebase SDK to write directly to Firestore: promote themselves to `SUPER_USER`, approve their own pending account, or delete/edit any tenant application, asset, or payment record. Every "only SUPER_USER can do X" check in the React code (SettingsPanel, ApplicationDetails, AssetRegistry, OverviewDashboard) is a UI convenience, not a real permission boundary. This is the single most important fix — it undermines every other access control in the app.

**2. Assets can be double-allocated to two tenants.** Both `ApplicationDetails.handleAllocate` and `AssetRegistry.executeAllocation` write an allocation without re-checking, at write time, that the asset is still vacant. Two staff members (or one staff member with two open tabs) allocating around the same time can both succeed — the same physical store or unit ends up promised to two different tenants, and there's no error to catch it.

**3. Staff can get logged out on every page refresh due to a timing race.** The effect that resolves "who is this signed-in user" runs against whatever's in the local `users` list *right now* — but that list loads asynchronously from Firestore. If the resolve check runs before the `users` data has arrived, a legitimately registered staff member gets told their email "is not recognized" and is signed back out. This likely explains (or contributes to) the login issue you just hit, and will keep recurring for other staff unless fixed properly rather than worked around.

**4. Dashboard "Collected Revenue" and "Projected Revenue" figures are fabricated.** They're computed from occupancy counts × standard rates, never from the real `payments` records already stored on each application. A finance officer looking at this dashboard is looking at an estimate that could be significantly wrong in either direction, not actual collected cash.

**5. Printed rent bill numbers are random and not saved anywhere.** A new bill number is generated with `Math.random()` every time the print modal re-renders, and it's never written back to the record. The number on a printed bill may not match what's shown next time, and there's no durable link between a bill number and the bill it was printed for — a real problem for an official financial/legal document.

**6. Concurrent payment entries can silently overwrite each other.** Logging a new installment payment reads the current payments array, appends to it, and writes the whole array back. If two staff log a payment for the same tenant close together, the second write can overwrite the first — a recorded payment just disappears, no error, no trace.

**7. The SMS endpoint has no authentication and no rate limit.** `/api/send-sms` on the Express server will send an SMS (real money, via Wigal) for anyone who can reach it — it doesn't check that the caller is a signed-in staff member, and there's no cap on volume. It's an open, unmetered relay sitting on the same server as the app.

**8. The compiled server code is being served as a public static file.** I verified this myself: the build puts `dist/server.cjs` and `dist/server.cjs.map` in the same folder as the frontend files, and the production server serves that entire folder as static content. That means anyone can currently download your backend's compiled JavaScript — and the sourcemap, which reconstructs the original TypeScript source — just by visiting `/server.cjs.map` on your VM.

## High

- **"Unlink all assets" can leave a stale allocation.** A bug in the removal-set comparison means unlinking every asset from an application doesn't actually clear the application's status, so the app still looks reserved while the registry shows the asset as vacant — free for a second allocation.
- **Two different, disagreeing models of "which assets does this tenant hold"** exist between `ApplicationDetails.tsx` and `AssetRegistry.tsx`. Releasing one of several assets via the registry screen can wrongly reset a still-active tenant back to square one.
- **None of the allocate/unlink/payment writes are transactional.** Every one of these flows does 2+ separate Firestore writes with no `runTransaction`. A dropped connection between writes leaves the application and its asset(s) disagreeing permanently.
- **Scanned agreement uploads accept files up to 3MB, but Firestore documents cap out around 1MB.** Anything over roughly 700KB will fail to save with a confusing error, despite passing the stated size check.
- **CSV exports are vulnerable to formula injection.** Applicant-entered fields (name, address, etc.) flow into CSV exports without neutralizing a leading `=`, `+`, `-`, or `@` — a malicious value can execute as a formula when a staff member opens the export in Excel.
- **No server-side validation on the SMS/registration destination number or message length** — compounds finding #7 above.
- **Dashboard revenue-analytics delete action is available to more roles than intended** — gated by "not a REGISTRAR" rather than an explicit allow-list, so LEASING_OFFICER and FINANCIAL_OFFICER can also permanently delete applications from that screen.

## Medium (selected — the full list from each reviewer is longer)

- Deleted applications never disappear from the live dashboard until a full page reload (the local merge map never removes entries for deleted documents).
- A leftover placeholder `SUPER_USER` seed account (`edwin@zamsonia.com`, `ACTIVE`) is still auto-created whenever the `users` collection is empty — a stray scaffolding account with full admin rights.
- Non-numeric installment amounts pass validation as `NaN` and corrupt totals.
- Annual bulk-billing can include tenants who haven't moved in yet (`AWAITING_PAYMENT` status), sending "your annual rent bill" before their first payment.
- A false "100% delivery success" is shown on the SMS dashboard when zero messages have ever been sent.
- Category-track renames in Settings orphan the old Firestore document instead of updating it in place.
- No `useMemo`/`useCallback` anywhere in the ~3,200-line dashboard component — every keystroke in any search box re-filters the full dataset for every tab, not just the visible one.
- Signature pad state can desync from the saved value on window resize/rotation, showing "not signed" while a stale signature is still attached to the form.
- A stock-photo "simulated portrait" picker is available unconditionally in the registration form's camera step — not gated to development/testing only, which is an identity-integrity concern for a Ghana Card-linked government record.

## Low

Duplicated logic (rent-default constants, role→view routing, filter predicates, bill-printing markup) repeated 3–5 times across files; heavy `TypeScript any` usage on data flowing from Firestore; a handful of dead code paths and unused imports; missing size caps on camera photo uploads; inconsistent asset-code sanitization when used as Firestore document IDs; `tsc --noEmit`'s `include` only covers `src/**/*`, so `server.ts` itself is never typechecked in CI.

---

## Suggested approach

Given the scale, I'd suggest we don't try to fix all ~50 findings in one pass. My recommendation for a first round, in order:

1. Lock down Firestore rules with real role checks (critical #1) — this is the foundation everything else's access control depends on.
2. Fix the double-allocation race with transactions (critical #2, high items #1–3).
3. Stop serving the server bundle as a static file, and lock down the SMS endpoint (critical #7, #8, high items).
4. Fix the login race condition (critical #3) properly, and remove the placeholder seed admin (medium).
5. Fix the fabricated revenue numbers and bill-number generation (critical #4, #5) and the payment-overwrite race (critical #6) — these affect trust in financial records.

Everything else (medium/low) can follow in later passes once the above is solid.
